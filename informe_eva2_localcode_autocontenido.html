1. Introducción

Este informe presenta el desarrollo de pruebas aplicado al sistema LocalCode, correspondiente al repositorio mi-leet-code-cs50. Para esta evaluación se utilizó el problema Mario en lenguaje C, ya que permite revisar funcionalidades importantes como Run Code, Submit, manejo de errores, usabilidad, rendimiento básico e integración entre frontend y backend.

El trabajo se organiza mediante un Plan Maestro de Pruebas, casos de prueba, criterios BDD, matriz RTM, evidencias y hallazgos. La finalidad es aplicar de forma práctica los contenidos vistos en clases y documentar los resultados obtenidos durante la revisión del sistema.

2. Plan Maestro de Pruebas

2.1 Objetivo del plan

El objetivo del Plan Maestro de Pruebas es organizar la estrategia de testing aplicada a LocalCode, definiendo el alcance, tipos de prueba, criterios de entrada y salida, casos de prueba, riesgos, evidencias y recomendaciones.

2.2 Alcance de las pruebas

Dentro del alcance

  • Problema Mario en lenguaje C.
  • Editor de código de LocalCode.
  • Botones Run Code y Submit.
  • Manejo de errores de compilación.
  • Comunicación frontend-backend.
  • Usabilidad y accesibilidad básica.
  • Rendimiento básico.
  • Seguridad básica/endpoints.

Fuera del alcance

  • Probar todos los problemas de LocalCode.
  • Modificar el código fuente interno del sistema.
  • Realizar pruebas de carga con muchos usuarios.
  • Hacer pentesting avanzado.
  • Automatizar pruebas con herramientas externas.
  • Desplegar el sistema en producción.

2.5 Estrategia de pruebas

La estrategia utilizada corresponde a un plan de pruebas basado en riesgos, ya que se seleccionan las funcionalidades más importantes del sistema y se prueban según su impacto.

Run Code

Permite ejecutar el código durante el desarrollo.

Submit

Corresponde al envío final de la solución.

Manejo de errores

El sistema debe responder sin caerse.

Editor

Afecta directamente la experiencia del usuario.

Frontend-backend

Permite recibir la respuesta del servidor.

Seguridad/endpoints

No debería exponer información sensible.

Para las pruebas funcionales se utiliza la técnica de caja negra, ya que se evalúa el comportamiento visible del sistema mediante acciones y resultados esperados, sin revisar línea por línea el código interno de LocalCode.

Hallazgo principal

El principal hallazgo identificado corresponde a la usabilidad del editor de código. El espacio del editor es reducido, lo que dificulta visualizar el código completo, revisar errores pequeños y modificar líneas de forma rápida. Además, al ejecutar Run Code, el sistema muestra el resultado general, pero no presenta la salida completa generada por el programa.

Recomendación

Se recomienda ampliar el área visible del editor, agregar una opción de pantalla completa y mostrar la salida generada junto al resultado Accepted o Failed, para entregar una retroalimentación más clara al usuario.

7. Conclusión

Se concluye que el sistema LocalCode funcionó correctamente dentro del alcance definido para esta evaluación. Las pruebas realizadas permitieron validar funcionalidades importantes como Run Code, Submit, manejo de errores, integración frontend-backend, rendimiento básico y seguridad/endpoints.

Los resultados principales fueron positivos, ya que el sistema respondió correctamente y no presentó fallas críticas. Como hallazgo, se identificó una oportunidad de mejora en la usabilidad del editor de código, debido a su tamaño reducido y a la falta de visualización de la salida completa generada por el programa.

Por ello, se recomienda mejorar el editor y entregar mayor retroalimentación visual al usuario.

Anexo — Código utilizado en el problema Mario

#include <stdio.h>

int main(void)
{
    int altura;
    scanf("%d", &altura);

    for (int fila = 1; fila <= altura; fila++)
    {
        for (int espacio = 0; espacio < altura - fila; espacio++)
        {
            printf(" ");
        }

        for (int bloque = 0; bloque < fila; bloque++)
        {
            printf("#");
        }

        printf("\n");
    }

    return 0;
}
